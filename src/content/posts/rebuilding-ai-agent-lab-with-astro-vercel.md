## 为什么要重建

旧站点已经可以通过 GitHub Pages 访问，但它更像一次快速实验，而不是一个可以长期运营的内容系统。真正的问题不在“能不能打开”，而在后续每周发布、搜索收录、广告审核和维护成本是否可控。

这次重建前，仓库里存在几个明显信号：

- `main` 分支跟踪了大量 `public/` 生成文件。
- `node_modules/` 曾被提交进仓库，导致文件数量膨胀。
- `gh-pages` 分支上有 sitemap 和 robots 修补，但源分支没有稳定生成逻辑。
- 站点还保留 Hexo 默认的 `hello-world` 样板文章。
- 内容定位还停留在“OpenClaw 自动进化笔记”，没有扩展成可持续的栏目体系。

这些问题单独看都能修，但合在一起说明：与其继续补丁式维护，不如把站点换成面向运营的静态内容架构。

## 为什么选择 Astro 和 Vercel

Astro 的优势是内容站友好。文章可以保存在 Markdown 内容集合里，构建时生成静态页面，页面级 SEO 元数据也容易统一处理。

Vercel 的优势是发布链路简单。GitHub 推送后自动构建，后续接入自定义域名、预览部署和环境变量都比较自然。对这个项目来说，部署平台不应该成为主要工作量，内容质量和运营节奏才是。

这并不是说 Hexo 不好。Hexo 适合快速搭建博客，也有丰富主题。但当前目标已经从“搭一个博客”变成“运营一个可审核、可收录、可长期维护的内容站”。Astro 更适合这个阶段。

## 这次重建补了什么

工程层面，重建后的站点具备以下基础：

- 文章、分类、标签、关于、联系、隐私政策、免责声明页面。
- RSS、robots、sitemap 自动生成。
- 文章页输出 canonical、Open Graph 和 `BlogPosting` JSON-LD。
- 构建产物和依赖目录不再进入 Git。
- GitHub Actions 改为验证 Astro 构建，而不是直接发布到 `gh-pages`。
- Vercel 配置明确 `dist/` 为输出目录。

运营层面，站点也补上了发布前检查：

- 原创性检查：不发布采集、洗稿或拼接内容。
- 事实检查：涉及平台政策、价格、服务能力时要确认来源和日期。
- AdSense 风险检查：避免薄内容、空模板页、误导性标题和用户生成内容风险。
- 人味检查：删掉夸张口号，保留具体动作、限制和失败过程。
- 构建检查：发布前必须跑本地构建。

## 首版不做什么

这次没有接入评论系统。评论会引入用户生成内容审核责任，对一个准备申请广告的新站不划算。

这次也没有直接接广告代码。站点需要先积累足够原创内容和可信页面，再申请 AdSense。过早放广告位，只会让页面看起来像为变现而搭的空壳。

同样，域名还没有直接购买。当前只生成候选列表，购买、预算和 DNS 所有权需要人工确认。等域名确定后，再把 `PUBLIC_SITE_URL`、Vercel 项目域名、Search Console 和 Bing Webmaster 一次性配齐。

## 下一步运营节奏

首月最重要的不是追热点，而是建立稳定栏目：

- AI Agent 工程日志：记录具体工具链和自动化流程。
- 部署与搜索增长：记录 Vercel、GitHub、域名、站长平台和 SEO 配置。
- 工具复盘：评价 Codex、OpenClaw、浏览器自动化和内容生产工具的真实边界。
- 广告审核准备：积累隐私政策、联系页、原创文章和站点结构改进记录。

每篇文章都应该能回答一个问题：读者看完后，能不能少踩一个坑，或者更清楚地判断某个技术选择是否值得做？

如果不能，就先不发布。
